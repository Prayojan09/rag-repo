# Architecture

The system is a modular monolith. FastAPI owns HTTP concerns, Pydantic Settings reads deployment configuration, SQLAlchemy 2.x owns PostgreSQL connectivity, and Alembic manages schema evolution. PostgreSQL stores uploaded document metadata and extracted text chunks; Qdrant stores dense vectors for similarity retrieval.

`GET /health` is a liveness check and does not depend on external services. `GET /ready` performs bounded PostgreSQL and Qdrant checks and reports each dependency independently. Exceptions return a generic 500 response; details go to server logs. API docs are served by FastAPI at `/docs` and `/redoc`.

The document API validates supported extensions and basic file signatures, enforces an upload size limit, hashes content for duplicate detection, and assigns monotonically increasing versions per filename. Originals are saved under generated storage keys; clients never control the filesystem path. In Compose, originals live in the `uploads_data` named volume. A chunk ID is deterministic for a document version, ordinal, and content. Chunk boundaries respect page/heading changes and configured character limits, with overlap for continuity. PDF pages and likely headings are extracted with PyMuPDF, including numbered module/chapter labels and short title-like headings when font sizes do not distinguish them; DOCX paragraphs, tables, styled headings, and bold short titles use python-docx; Markdown and common numbered/title-like headings are supported in TXT. Chunk context repeats the active heading and a detected trailing question into later answer chunks, including across page boundaries, while page provenance stays attached to the answer text. The extracted-content preview groups PDF chunks by source page and renders detected sections and list structure without displaying internal chunk identifiers.

The upload endpoint validates and stores the source, creates a queued PostgreSQL record, and returns while extraction, optional LLM-based display structuring, chunking, embedding, and indexing continue in a FastAPI background task with a separate database session. The structured Markdown preview is stored separately from the original extracted chunks and never replaces the evidence indexed for retrieval or citations. When enabled by an available LLM provider, up to the configured character limit of extracted document text is sent to that provider, adding cost and latency. Failures or oversized documents fall back to the original preview and do not block indexing. The frontend polls queued/indexing statuses and exposes retry for interrupted work. Ready documents can be reprocessed from their stored originals to regenerate extracted text and chunks after chunking logic changes; vector-only reindexing remains a separate action. This shortens the upload request but does not eliminate CPU time required to process large scanned files; these in-process tasks can be interrupted by an application restart, so a durable external job queue is a future scaling step. OCR is available for scanned pages and raster images. Deleting a document removes its rows (chunks cascade) and then removes its source file; a filesystem failure is logged and can leave an orphaned file for later cleanup.

Dense retrieval encodes text with the configured Sentence Transformers model and normalizes embeddings. Qdrant stores one point per chunk, keyed by the stable chunk UUID; point payloads contain only document/chunk identifiers and basic version metadata. Collection names include a hash of model name and revision to prevent accidental vector mixing across configured models. Search can filter by document IDs, then resolves hit IDs back through PostgreSQL and returns only chunks belonging to documents currently marked `ready`. This SQL check also prevents stale Qdrant points from being returned after a failed deletion or reindex.

Keyword retrieval uses Okapi BM25 (`rank-bm25`) over ready PostgreSQL chunks, tokenizing Unicode words case-insensitively and including the chunk heading in its searchable text. The corpus is built per request, which avoids index drift and works for small deployments but scans all eligible chunks; larger deployments should move to a persistent/incremental keyword index and benchmark its update consistency. `POST /api/v1/search` supports dense-only, keyword-only, and hybrid modes. Hybrid mode retrieves configurable candidate lists from each method and fuses their one-based ranks with Reciprocal Rank Fusion, `sum(1 / (rrf_constant + rank))`. The API returns component ranks/scores to make retrieval behavior inspectable; the fused score is a ranking signal rather than a calibrated probability.

Cross-encoder reranking is an optional second stage for search and the default for chat. It scores each `(question, passage)` pair from the retrieved candidate set and sorts by the model's relevance score. This is more compute-intensive than vector retrieval, so candidate depth and batch size are bounded and configurable; model weights load lazily from Sentence Transformers. Raw reranker outputs are model scores, not probabilities.

Chat retrieves candidate passages, reranks them, then calls an LLM through a provider protocol. The current adapter speaks the OpenAI-compatible Chat Completions JSON mode; endpoint, model, API key, timeout, and output limit are environment settings. The prompt treats retrieved text as untrusted data and requests cited claims, explicit conflicts, or abstention. Response parsing checks the answer shape and rejects chunk IDs that were not retrieved, then resolves citations to PostgreSQL source metadata. A second call to the same configured LLM checks every claim and conflict description against only its cited passages. Only statements marked supported are returned, and answer prose is rebuilt from those checked statements; a missing, malformed, or incomplete verifier response causes abstention. The LLM verifier is fallible, so this is a defense layer rather than a proof of correctness; evaluation must measure false support and missed support. Verification adds a second LLM request, latency, and possible provider cost whenever statements are generated. If retrieval returns no passages, chat abstains without calling the LLM. Ingestion and search do not require LLM credentials.

Ingestion stores extracted chunks first with an `indexing` status, upserts vectors, then marks the document `ready`. The upsert is idempotent. If indexing fails, the document becomes `failed` and can be retried from the original file or reindexed from stored chunks. Deletion commits relational removal first and then deletes vectors; if Qdrant is unavailable, stale points remain physically stored but SQL validation prevents them from appearing in search. Embedding weights load lazily and are cached by Sentence Transformers; Compose persists the model cache separately from application files.

The readiness probe checks Qdrant's `/readyz` endpoint and PostgreSQL `SELECT 1`. API credentials resolve to tenant IDs: `API_ACCESS_TOKEN` maps to `default`, while `API_TENANT_TOKENS` maps multiple tenant IDs to separate tokens. Tokens are compared in constant time. SQL document, chunk, citation, and feedback access is tenant-filtered; Qdrant points carry tenant metadata and searches/deletions use tenant filters. Existing points without a tenant field remain visible only to the `default` tenant for migration compatibility. Health probes remain public. Chat feedback stores an opaque answer ID, rating, optional comment, timestamp, and tenant ID without persisting question or answer text. Compose credentials are intentionally development-only.

Evaluation code lives under `app/evaluation` and `scripts/evaluate.py`. A versioned fictional dataset labels relevant chunks, key answer facts, and questions that should abstain. Retrieval modes run against a temporary SQLite corpus and in-memory Qdrant so evaluation does not modify user documents or the configured vector collection. Dense and reranked comparisons use the configured production Sentence Transformers models. Optional chat evaluation is an explicit CLI opt-in because it sends real prompts to the configured provider and may incur charges. Its key-fact score is exact substring recall, not a full semantic correctness judge; production datasets need human-reviewed labels and answer review.

## Phase 10 hardening

Each configured bearer token maps to exactly one tenant scope. The `0004_tenant_isolation` migration assigns existing PostgreSQL documents and feedback to `default` and changes document uniqueness to be tenant-local. New Qdrant points include `tenant_id`; retrieval and deletion include matching filters. API tests verify cross-tenant document listing, detail, citation, keyword search, and deletion isolation. This is workspace-level isolation, not individual user identity, roles, or document ACLs. Protect tenant tokens and use TLS/network controls at deployment ingress.

Upload parsing runs in a worker thread; request bodies, chunk sizes, BM25 corpus size, candidate count, reranker batches, LLM output size, and provider retries are bounded by settings. LLM retries apply only to transient HTTP/server and transport errors. Retrieved passages are explicitly treated as untrusted prompt data. Requests carry an `X-Request-ID`; generic error responses avoid exception details while server logs record the error type and request ID. The container runs as an unprivileged user, has a readiness healthcheck, and Compose services restart after failure.

Operational limits: ingestion and model inference still run inside the API process, so scale-out, long jobs, and stronger CPU/memory isolation need measured deployment-specific sizing. API credentials are static bearer tokens without rotation or user roles. Compose exposes local service ports and includes development-only PostgreSQL credentials; do not expose this configuration to the internet. PostgreSQL, Qdrant, and uploaded source files need coordinated, tested backups. Prompt-injection instructions reduce risk but cannot guarantee that a model ignores malicious document content.

The browser interface is a React/Vite client that calls the existing `/api/v1` endpoints. Local Vite development proxies API and health requests to FastAPI at port 8000; deployments can either proxy those paths on the same origin or set a public API base and explicitly allow the frontend origin through `CORS_ALLOWED_ORIGINS`. The bearer token is entered by the user and stored in browser local storage, so this UI is suitable for trusted internal clients; public multi-user deployments should replace static shared tenant tokens with an identity provider and safer credential/session handling.

## OCR and saved conversations

Uploads default to a 200 MiB limit. Text based PDFs use native extraction; pages without selectable text use PyMuPDF OCR backed by the system Tesseract executable. Common raster images are opened as one or more pages and OCRed into the same provenance-aware chunk pipeline. OCR work is capped at 500 pages per file and 100 million page pixels; language and DPI are configurable. Local Python installations must install Tesseract and language data, while the backend Docker image installs English Tesseract support. Qdrant request timeouts are configured separately from the short dependency health check timeout so larger vector uploads have time to complete.

Conversation headers and messages are stored in PostgreSQL through Alembic migration `0005_conversations`. Each conversation is tenant-owned; list, read, delete, and chat append operations filter by the authenticated tenant. For each chat request, the API loads at most the eight most recent messages from that exact conversation ID; it never accepts history supplied by the browser or loads messages from another conversation. Recent turns help interpret follow-up questions and retrieval references, but are explicitly not evidence for factual claims. Assistant messages store the structured response JSON, so the UI can restore citations and feedback context when users reopen history.
